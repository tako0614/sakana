# Evexの継続的な記憶整理

この文書は実装・運用手順。設定やジョブの作成だけでは、本番反映や全履歴の処理完了を示さない。

採用したWriter・API・継続処理の契約は[Writer設計](writer-design.md)。npm公開・Docs配信・本番Bot稼働は、それぞれ検証して反映状態を記録する。

対象はEvex Developers (`1255359848644608035`)。既存Botの中に、原資料・索引のworkerと、AIによる整理のworkerを分ける。別Bot、外部DB、ライブラリ内のスケジューラーは追加しない。Atomの本文・関係・版・認可・検索の責務は維持する。

## 入力と読み出し

原文アーカイブは保つ。Bot投稿を一律に削除せず、本文・embedのfields・添付メタデータを含めて判定する。同じWriterが原文と前後関係を調べ、出来事への反映、文脈としての処理、完全重複の対応先、続きが必要な範囲を決める。独立した選別LLMは置かない。否定、バージョン、状態の差は同じ投稿として潰さない。判断前のBot投稿を自動想起へ流さない。

連続する人間の発言は文脈をまとめるが、各message ID、返信先、引用者を残す。直近のコンテキストは新しい側から予算を取り、表示順は時系列に戻す。ピン留めや人間から返信された発言は単純な重複除去より優先する。圧縮先は同じサーバー・チャンネルの、現在も保持対象の直接の代表に限る。

自動想起は現在のcontext、明示的なthought、取得した観測を使う。自動で別の質問へ書き換えない。読める範囲は現在のチャンネルと、当該利用者とBotの両方が読めるEvexの公開チャンネル。他の非公開チャンネルや他サーバーの記憶は混ぜない。モデルへ送る直前と応答後に、記憶・原資料・権限を再確認する。

## モデルと費用

- 出来事の整理: `inclusionai/ling-3.0-flash:free` が実際に利用可能なら優先し、同じモデルの有料版 `inclusionai/ling-3.0-flash` へフォールバックする。別モデルを選ぶ無料ルーターは使わない。
- 埋め込み: OpenRouter `qwen/qwen3-embedding-8b`、既定4096次元。本文はそのまま、検索入力には現在の文脈に関する短い検索instructionを付ける。E5のquery/passage接頭辞は使わない。[Qwen公式](https://github.com/QwenLM/Qwen3-Embedding)と[OpenRouter Embeddings API](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings)に従う。
- EvexのLingと、文書・検索入力のQwenは同じ永続予算へ計上する。上限は30 USD。日付変更・再起動でリセットせず、実請求が分からない呼び出しは予約額を残す。未確定予約のため、実請求30 USDより前に停止することもある。
- 他サーバーの呼び出しはEvexの予算を使わない。Dream対象以外のAtom検索と既存のアーカイブ意味検索は従来のローカルE5を使う。

呼び出し前にOpenRouterのendpoint料金を検証し、その上限で予約する。無料routeの不在・混雑は短期間覚える。401/402を別モデルへの切替で回避しない。詳細は[共通の費用記録](memory-cost.md)。

QwenはE5と別の索引識別子を持つ。旧索引はQwenの候補に使わず、新しいベクトルが揃うまで語彙検索も併用する。Writerの完了チェックにもエンコーダー識別子を残す。4096次元は384次元より保存・探索の費用が大きく、現行AtomのJSONベクトル保存と1 revisionずつの索引APIでは、全履歴の所要時間・ディスク容量を実測する必要がある。ドル上限は容量・速度の保証ではない。

## 継続処理

初回は取得可能な全履歴を対象に、許可範囲ごとに古い発言から最大60件・60KBずつ整理する。公開範囲はチャンネルをまたぐ時系列、非公開範囲はそのチャンネル内を扱う。日単位に分割して待たず、再開可能なジョブとして続ける。初回履歴、新着、定期見直しのうち実行可能な作業へ順番に時間を割り当てる。新着は60秒の静穏時間を待つ。

毎日04:00 JSTに現在の生成Atomの有限な見直し対象を作る。最大4バッチという上限は設けない。各対象の観測版・根拠・関係・目的を記録し、同じ対象を重複して処理しない。Agentが必要な既存Atomや原資料をたどり、変更案と未解決の続きがあれば返す。原文のhashと、処理済み等の状態を分離する。

一仕事あたり最大8回のモデル送信、6回のtool実行。送信回数はフォールバック・再試行を含めて送信前に永続化する。通信失敗は有限回で保留し、同じ入力で失敗が3回続けばheldとして未解決のまま残す。出典投影や索引待ちは失敗に数えない。失敗した仕事を捨てて全件完了とはしない。

AI workerはAtomの編集を確定して索引更新を要求する。原資料・索引workerだけが原資料同期とベクトル生成を実行し、永続化を確認する。索引の確認前には処理対象の世代を完了にしない。

## 操作

`.env` で `MEMORY_DREAMING_ENABLED=true`、`MEMORY_DREAMING_GUILDS=1255359848644608035`、`OPENROUTER_API_KEY` を設定する。初回はBotを停止した保守作業で全履歴取得を検証する。起動中のBotと原資料同期CLIを同時に走らせない。

初回取得の証明には、通常チャンネル・active thread・取得可能なarchived threadを列挙し、最後まで取得できた記録が必要。昔のローカル件数だけでは開始しない。API障害・途中ページ・キャンセルがあれば証明を更新し直す。

```sh
# status/start/pause/resumeはDiscordに送信しない。startは仕事を登録するだけ。
npm run memory:organize -- --status --guild 1255359848644608035
npm run memory:organize -- --start --guild 1255359848644608035
npm run memory:organize -- --pause --guild 1255359848644608035
npm run memory:organize -- --resume --guild 1255359848644608035
```

`--start` は同じ予算・取得済み範囲を再利用し、二重の初回ジョブを作らない。`--resume` は既存予算の累計を消さない。Bot内のworkerが仕事を進めるので、CLIで二つ目のWriterを動かす必要はない。

初回完了は、取得範囲の証明、対象世代すべての処理結果、未解決失敗の不存在、Atom確定、現在の索引、永続化の確認で判断する。worker起動・API成功・処理累計だけを完了としない。運用時は `--status` の予算・残数・失敗・phaseとserviceの実行版を一緒に読み戻す。
