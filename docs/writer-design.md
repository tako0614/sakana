# Writer：出来事を既存のAtom構造へ記録する

状態：2026-09-13の採用設計。Atom 0.9とSakanaの実装契約。[運用手順と反映状態](dreaming.md)を参照。

## 中心に置く仕事

Writerは、会話や資料に現れた出来事・事象を、意味を取り違えず読み出せる粒度で記録し、現在のAtom構造へ結び付ける。

既存の構造を読みながら、新しい出来事、その続き、訂正、繰り返しを整理する。人、プロジェクト、議題、出来事、そのまとまりも普通のAtomで表せる。新しい必須メモリ型や専門Agentは増やさない。

既存の構造は整理の手がかりになる。ただし、似たAtomへ無理に当てはめない。今回初めて分かった事象なら、新しく記録してよい。

## ちょうどいい解像度

基本単位は「後から一つの出来事として取り出せるまとまり」。メッセージ数、日付、入力バッチの大きさでは決めない。

- 同じ出来事を説明する連投や返信は、複数の原文を根拠として一つのAtomへまとめられる。
- 一つの投稿が別々の出来事を含むなら分ける。
- 条件・否定・対象時刻・誰の観測や発言かは、意味に必要な範囲で本文に残す。条件だけを切り落とした短文にしない。
- ある部分を別に参照・更新したい、別の出来事でも共有したい、異なる立場や条件を混ぜると誤解する、という場合に子Atomや関係へ分ける。
- 単独で扱う理由がない細部は本文に含める。全ての発言や文節を必ず別Atomへ分解しない。

粒度は後から調整できる。一つの出来事の詳細が増えたら、元のAtomを概要として残して詳細を分けられる。まとめ直す場合も、元の根拠と参照先を失わないように編集する。これは必ず実行する階層化ではない。

## 具体例

既に「Evex Bot」と「メモリ検索」のAtomがあるとする。次の発言は説明用の架空例。

1. Aが「昨日からメモリ検索でエラーが出る」と投稿する。
2. Aが続けて「長い入力のときだけ」と補足する。
3. Bが返信して「自分の環境でも再現した。タイムアウトかもしれない」と報告する。

初めは「Aが前日から長い入力でメモリ検索のエラーを報告し、Bも再現を報告した」という一つの出来事として記録できる。「タイムアウトが原因」は確定していないため、残すならBの推測として明記する。時刻は原文の投稿日時と区別して扱う。

この出来事を既存の「Evex Bot」「メモリ検索」へ結び付ける。人名ごと、文節ごと、投稿ごとに必ずAtomを増やす必要はない。AとBの環境差が後で重要になれば、各報告を個別に参照できるように分ける。

次の日に「入力長制限を修正した」「修正後は再現しない」という報告が来たら、同じ出来事の経過として関連付ける。障害発生、修正作業、修正後の確認を別々に取り出す必要があれば、詳細Atomを作り、出来事の概要を更新する。過去の障害記録を「エラーは存在しなかった」へ書き換えない。修正報告だけで原因まで確定したことにもしない。

一週間後に似たエラーが発生した場合は、新しい発生として記録し、以前の出来事との関係を付ける。同じ文面でも別の時点の出来事は消さない。同一障害の継続なのか再発なのか不明なら、その不明さを保つ。

## 一回ごとの判断

Writerは、次の流れを継続する。

1. 原文を、実際の返信先・前後の会話・添付の読取状態と一緒に読む。
2. 今読んでいる内容を文脈として、既存の出来事や関連Atomを検索する。必要なAtomと原資料を確認する。
3. 同じ出来事の補足、別の出来事、訂正、関連する現象のどれとして扱うか判断する。
4. 必要なAtomと関係を追加し、同じ出来事の説明やまとまりを必要な範囲で更新する。
5. 原文への対応と続きの調査箇所を残し、次の読取・編集へ進む。

同じ出来事への追記と、情報の同一視は分ける。別人による報告を一つの出来事へまとめても、その報告者と根拠は残す。反論・訂正・見解の違いが意味を変えるなら、それぞれを区別して結び付ける。

同じ出来事かどうかは、対象、時期、実際の返信やスレッドの続き、明示された障害・リリース等の識別子を手がかりにする。一つの手がかりだけで同一と決めず、根拠が足りなければ無理に統合しない。

継続する性質や傾向も事象として記録できる。複数の出来事から「繰り返し起きている」という傾向をまとめる場合は、元の各発生を参照して残す。一度の発生から、恒常的な性質や原因を勝手に作らない。

「既存Atomをそのまま利用する」も正常な結果とする。新Atomを必ず作らせない。ただし、別の発生や別の発言を、文面が似ているだけで既存Atomに吸収しない。

関係には理由が必要。同じ話題への所属、同じ出来事の続報、明示的な返信などを、原資料に照らして付ける。ベクトルが近いだけで同一事象や因果関係と認定しない。AIによるつながりの推測を事実へ混ぜない。

## 継続と入力の節約

サーバーの全履歴を対象とする一つの継続的な整理作業にする。一回のモデル呼び出しでは読める量を区切り、Writerが必要な前後・関連する過去を追加で読めるようにする。読み込んだ一組を、そのまま永続的な話題や見直し単位にしない。

全履歴を一度にプロンプトへ入れるという意味ではない。未処理範囲はホストが保持し、Writerが関心のある話題だけを巡って他を未読のまま終えないようにする。中断時は、対象の出来事、確認した参照、未解決事項、次に読む位置を短い作業状態として残す。これは知識Atomや非公開の思考過程の保存ではない。

Botの投稿も内容で扱う。無変化の定型通知は、代表と発生時刻・件数などの対応を保持して入力を圧縮できる。障害、リリース、状態変化、人が反応した通知は出来事の根拠になり得る。意味のある差分を単純な重複として落とさない。連投は会話としてまとめて読み、各原文の発言者と返信関係を保つ。

原文はアーカイブに残す。独立した出来事を追加しない相槌などは会話の文脈として扱えるが、事前の粗いAI選別でWriterから意味判断の材料を取り去らない。

対象原文には、どのAtomに反映したか、文脈として扱ったか、重複の対応先、まだ続きが必要かを残す。これは処理漏れを見つけるための記録であり、モデルが意味を完全に理解した証明ではない。一部だけ記録できた原文は、残りを保留して全体を完了扱いしない。

読取件数・出力件数・費用の上限は、一回の作業を区切る。上限に達したことを、出来事の整理が終わった理由にはしない。「毎日4バッチ」は見直し対象の原理にせず、頻度と費用は別途決める運用設定とする。

## ライブラリとAgentの境界

Atom Memoryは `read / search / inspect / write` を提供する。モデル、ツールのJSONスキーマ、原資料取得、反復、費用、スケジューラーはSakanaが持つ。

`write({ changes }, { idempotencyKey })` は一回の変更案を原子的に保存する。create・revise・retireを同じ配列で表し、create/reviseでは本文・出典・リンクをすべて明示する。reviseのtargetは観測版の参照。配列内の参照はlocal IDで結び、順番のために意味構造を木へ制限しない。同じAtomへの複数変更は拒否する。旧create専用writeとcallback editは公開APIから除く。

各生成変更は、実際のモデル呼び出し前にホストが発行したInputTokenを持つ。最終payload、表示した本文、追加取得した原資料、持ち越した入力を結び付ける。同じモデル入力から生成した変更には同じtokenを使う。commitへ同居したことだけで、別の生成の依存を増やさない。

`inspect(ref, { direction, roles, limit, cursor })` は根と一段の近傍を返す。既定は正引き・逆引きの両方向。近傍には本文と、方向・役割・観測/論理参照・required・順序がある。Agentはそこで新しく発見した参照を使って次を読む。limit=0なら根だけ読む。権限のない近傍の存在や件数は返さない。親や構成という意味はWriterが本文と関係から判断し、ライブラリがrole名から勝手に推測しない。

## Sakanaの継続契約

Writerは `memory_search / memory_inspect / source_read / source_search / source_context` で調査し、最後にchanges・sourceOutcomes・continuationを返す。原資料検索はサーバーと許可範囲に束縛したkeyset cursorを使う。未投影の資料は原文として調べられ、モデルへ渡す前に出典投影を待つ。資料待ちは失敗回数へ加算しない。

sourceOutcomesは対象の各世代について、Atomへ反映したincorporated、独立Atomを作らないcontext_only、代表を指定するexact_duplicate、残作業を示すcontinuationのいずれか。context_onlyとexact_duplicateは空のchangesを許す。対象を省略して全体完了にはできない。後から見つけた原資料も依存と再開状態へ加える。

公開チャンネルは同一サーバーのpublic policyへ別投影し、その中で結び付ける。公開投影の全チャンネルを現在読める利用者だけが共有グラフを読める。一部でも読めなければチャンネル別投影を使う。非公開チャンネルはそれぞれ分離する。公開範囲の縮小は共有権限世代を失効してから原資料と依存Atomを消去する。

本文のhashと処理状態は別にする。pendingからretainになっただけで、その原文を読んで書いたAtomを失効させない。実際の編集・削除は原文投影と依存する生成を無効にする。自動readでは未受理のBot原文を渡さない。

一つのWriterが初回履歴、新着、定期見直しへ順番に作業時間を割り当てる。毎日04:00 JSTに、現在の生成Atomの版・根拠・関係・目的から有限の見直し対象を作る。4バッチ上限は置かない。入力が同じ見直しを重複して課金しない。

owner・lease・fenceを持つclaimが仕事を実行し、heartbeatと全終了処理でその所有を検証する。計画、InputToken、idempotencyKey、原資料hash、参照とcursorを保存してからcommitする。commit済みでも結果対応の保存前なら同じwriteを再送し、operationIdと参照を回収する。ソース世代・索引・永続化を確認してから対象を完了とする。

## 検証と採用の限界

型・実装・docs・失敗試験を同じ契約へ揃える。検査対象は、一括変更の原子性と重複防止、一段ずつの未知Atom発見、条件と原文対応、公開/非公開分離、権限失効、入力・関係の更新、claim奪取、中断後の続行、索引待ち、費用上限。

決定的な試験と、実際のLingで出来事・条件・再発を適切に記録できるかは別の評価にする。日をまたぐ続報、別時点の再発、曖昧な返信、条件付き提案、訂正、変化するBot通知で意味品質を調べる。同じ入力を違う位置で区切った比較は、主要な出来事・条件・根拠で評価し、文章やAtom IDの一致は要求しない。

新しい必須型、独立した選別Agent、固定の主張分類、強制的な階層、成功率による意味構造の再編は加えない。中心は、出来事を読み、既存の構造へ記録し、必要な次の箇所をたどる一つのWriterである。
