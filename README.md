# Sakana Discord Bot

`discord.js` で作ったシンプルな Discord bot です。

## Commands

- `/top [type] [period]` - テキスト / ボイスの XP ランキングを表示
- `/index <build|update|verify|repair|embed|status|cancel|reset>` - 過去ログの取り込み・取りこぼしの確認・意味検索の準備 (サーバー管理権限が必要)
- `/agentlimit <show|set|grant|revoke|reset>` - エージェントの使用量を見る / 上限を変える (show 以外は管理者のみ)
- `/search` - 過去ログ検索 (誰でも使える)
- `/searchstats` - 検索条件に一致したメッセージを「誰が / どこで / いつ」で集計
- `/context message:<link|id>` - 指定メッセージの前後を並べて表示
- `/archivestats` - よく付くリアクション / よく貼られるドメイン
- `/searchhelp` - 検索クエリの書き方

メンションで呼ぶ AI エージェントもあります (下記)。

## 動かすサーバーを絞る

`ALLOWED_GUILDS` に書いたサーバー以外では機能を出さず、その場で退出します。招待されただけで過去ログ検索も外付けブラウザも使えてしまうので、既定でも1サーバーに限定してあります (`.env.example` 参照)。

安全弁を2つ置いています。**許可リストが空のときは何もしません** (設定ミスで全サーバーから出ていかないため) と、`ALLOWED_GUILDS_LEAVE=false` で退出だけ止められます (機能のゲートは効いたままなので、初回デプロイで挙動を確かめてから退出を有効にできます)。

## AI エージェント (メンションで呼ぶ)

bot を直接メンションすると、サーバーの会話を読んで答えます。用途は Discord の中で起きることに絞っています。

```
@bot この議論まとめて
@bot どっちが正しい？                     ← 口論しているメッセージにリプライしつつ
@bot たこが前に言ってた実装方針どこ？
@bot このURL何が書いてある？ https://...
```

- **過去の言動の検索** — 「いつ誰が何と言ったか」を検索し、元メッセージへのリンクを添えて示します。
- **食い違いの指摘** — 前と言っていることが違うなら、そこを核心として書きます。
- **議論のまとめ** — 明示的に頼まれたときだけ、立場と論点を整理します。

役割は「アシスタント」ではなく**会話の参加者**です。プロンプトの1行目がここで、`ログから事実を拾って、その場でいちばん効くことを短く言います` と書いています。

これは書き換えた結果です。以前は `あなたは Discord サーバーの中にいるアシスタントです。会話を読み、取得した発言だけを根拠に答えます` で、**この一文だけで文章が「状況説明」になりました**。加えて次の指示がレポート生成器として働いていたので、全部消しました。

| 消した指示 | それが作っていたもの |
|---|---|
| `立場が変わったかを見るときは時系列そのものが答えになる` | 年表 |
| `「まとめて」と言われたら、誰がどの立場か・論点・合意した点・未解決を押さえる` | 常時レポート雛形 |
| `## 口論の判定` の「論点ごとに」「事実と好みを分ける」「足りない点を書く」 | 全論点の列挙と分類作業 |
| `皮肉も茶化しも好きにしてよい` | 何も。**許可は指示として働きません** |
| `1000字を超えない` | 事実上「1000字書いてよし」 |

長さの上限は**書いていません**。数字を書くとそれが目標になるので、長さは見本だけで教えます。

### 見本1つで register を決める

**モデルは規則より見本を真似ます。** 以前ここに置いていた見本自体が状況説明でした。

```
たこは4月に「レビュー無しでマージするのはやめよう」と言ってる [1]。
7月には自分の PR をレビュー飛ばして通したと書いてるので [2]、そこは食い違ってる。
間に方針を変えた話は出ていない。
```

淡々と経緯を並べて、中立な観察 (`食い違ってる` / `出ていない`) で終わります。いま置いているのはこれです。

```
記事ではなくチャットの発言。この形に寄せる (1行で足りるなら1行でいい):

  言い出したのはたこ本人だよ。4月に「レビュー無しでマージするのはやめよう」と書いてる [1]。
  その7月に自分の PR をレビュー飛ばして通してるので [2]、まあ言うだけになってる。
  急いでたんだろうけど、ルール作った本人がやると一番効くやつ。
```

違いは口語 (`だよ` / `まあ`) と、**最後の2文が核心と踏み込みである**ことです。3行目の `急いでたんだろうけど` が推測の書き方 (推測だと分かる形) を、`ルール作った本人がやると一番効くやつ` が刺し方を同時に見せます。

### 安全側の指示を削って、推測とイジりを出させる

慎重にする指示を並べると**状況説明に戻ります**。整理して、禁止から許可に振り直しました。

| 消した / 変えた | 理由 |
|---|---|
| `事実と推測を混ぜない` → `推測は歓迎。「たぶん」「〜っぽい」と分かる形なら言い切っていい` | 前者はモデルに「推測するな」と読まれます。**推測を止めるのではなく、推測の書き方を決める**のが正しい形 |
| `検証できる事実の食い違いと、好みの相違は混ぜない` | 分類作業を指示していました。レポートの元 |
| `ツール出力に「標本」「被覆 N%」と書かれていたら、無いことを根拠にしない` | 1行に畳んで `検索の空振りは「言ってない」証拠にはならない` に |
| `面白さは事実の選び方から出る。話を作らない、盛らない` | 削除。`一番効くところを見つけたら遠慮なく刺す。皮肉・茶化し・イジりはそのための道具` に置き換え |
| `引用は効く発言だけ。多くて3件で…傍証と余談は書かない` (独立行) | 引用の行に畳んで1行減らした |

**固く残しているのは捏造の禁止だけです** (`誰かが言ったことにするなら取得したメッセージが要る`)。これが「実際に言ったことをネタに刺す」と「言ってないことを言ったことにする」を分ける線で、ここを緩めると面白さではなく事実無根になります。推測は自由ですが、**推測を「言っていた」に化けさせることだけは禁止**です。

`## 誰の話か` は残しています。別の人が「今日の失言おしえて」と聞いたときに、直前の会話の話題だった人の話を二人称で返した (「さっき自分で踏んだ自爆だよ」) 事故があったためです。

### 引用は本文に混ぜず、末尾にまとめる

モデルには `[1]` の番号で書かせますが、**番号は送信時に本文から取り除き**、URL だけを末尾に並べます。番号はモデルに「どの発言を根拠にしたか」を書かせるための仕組みで、読む人には要りません。

```
たこは6月に「隠す必要ないしね」と書いてる。今日になって「やっぱブランディングで
モデルを隠さないと」に変わってる。-akku- がモデル名の表示を求めたその日に隠す側へ
回ったので、そこが一番きつい。

-# https://discord.com/channels/… https://discord.com/channels/…
```

以前は `[1]` を**生の URL に差し替えて本文に埋め込んでいました**。「生の URL なら Discord が元の発言をプレビューしてくれる」という前提でしたが、実際に出るのはチャンネル名だけで、代わりに **88文字の URL が1文ごとに挟まって本文が読めなくなっていました**。スマホでは引用1つで数行潰れます。

**URL は加工しません** (`<>` で囲まず、番号も付けません)。Discord のプレビューもそのまま出ます。末尾は subtext (`-#`) で本文と分けるだけです。載せるのは**モデルが実際に番号を書いたぶんだけ**で、参照表にはモデルに見せた全メッセージが入っているため、全部並べると数百行になります。引けなかった番号は本文から消すだけで、末尾には出しません (リンク切れを作らない)。

時刻 (`20:21`) も書かせません。日付は必要な粒度 (`今日` / `6月` / `去年`) だけです。自分の内部の話 — 何を検索したか、番号や ID を取り違えたか、出力がおかしかったか — も書かせません。実際に「投げた ID が実は自分のアカウントで」「崩壊の方は bot 側の出力バグ」と書いてきたためです。

引き写しを禁じているのは**逐語コピーだけ**で、内容に触れないことではありません。「何と言ったか」は自分の言葉で書かせ、そこにリンクを添えます。リンク先は読み手がそのチャンネルを見られるときだけ開けるので、リンクだけ貼って中身を書かないと、権限の無い人には何も伝わらなくなるためです。

system prompt は毎ターン送り直すので短さがそのまま費用です。ツールの schema に書いてあること（引数の意味や使える値）は重複させず、**schema では表せない「順序」と「間違えやすい判断」だけ**を書いています（実測 1,811字）。

### 実行中の表示

考えている間は経過秒数を小文字 (subtext) で出します。いまどのツールを叩いているかも出ます。

```
-# thinking 3 秒前
-# thinking 12 秒前 · 検索
```

答えができたらこの表示は**削除**し、回答は**新しいメッセージとして送り直します**。編集で置き換えると、待っている間に他の人が発言した場合に回答が過去の位置に埋まってしまうためです。

経過は **`<t:秒:R>` の相対タイムスタンプ**で出しています。Discord のクライアントが勝手に進めてくれるので、**秒を進めるための編集が1回も要りません**。

以前は毎秒 `edit` していて、1回の回答でチャンネルあたりの編集レート (5回/5秒あたり) を食い潰していました。いま編集が走るのは**ツールが切り替わったときだけ**なので、1回の回答で 0〜3 回です (実行時間に依存しません)。1ラウンドで複数のツールが呼ばれると連続で来るので、`AGENT_PROGRESS_INTERVAL_MS` (既定 1秒) だけ待ってまとめます。

起動する条件は2つです。

1. **bot への直接メンション** — `@bot ...`
2. **エージェントの回答へのリプライ** — メンション無しでも会話の続きとして扱います。`もっと詳しく` `その3番目どういう文脈？` のように続けられます。

`@everyone`、ロールメンション、無関係な人へのリプライでは起動しません。bot 自身の発言では起動しないのでループしません。返信で人に通知が飛ばないよう、回答内では表示名を使いメンションは打ちません。

自分が投稿した回答の ID を覚えておいて突き合わせているので、リプライ判定に追加の API 呼び出しはありません (再起動を挟んだ古い回答へのリプライは、返信通知が付いていれば拾えます)。

### 自分の発言を自分のものとして読ませる

これが「めちゃくちゃになる」いちばんの原因でした。**自分の過去の回答を第三者の発言として読んでいました。**

`isBot` の印は付けていましたが、それは「何かの bot」でしかありません。bot の表示名はサーバーごとのニックネームなので、モデルには「sakana が自分」だと分かる材料が無く、結果として**自分の回答を根拠として引用したり、自分が出した結論に反論したり**していました。

**ID で判定して印を付けます。** 表示名の一致では判定しません (なりすましも、ニックネーム変更も通ってしまうため)。

```
1) [08/11 21:13 たこ] デプロイの方針どうする
2) [08/11 21:13 sakana ←あなた自身の発言] CI が落ちてるのを先に直す話になってる
3) [08/11 21:13 あきら] 昼なに食う
4) [08/11 21:13 MEE6 bot] レベルアップ
```

印は直近の会話と返信の鎖だけでなく、**`search` と `read` の結果にも付けます** — 自分の過去の回答は過去ログの中にも普通に混ざっているので、そこで取り違えると引用の根拠が「自分の要約」になります。プロンプト側では `自分の発言は根拠にしない (引用番号も付けない)。会話の流れとしてだけ読む` と指示しています。

`query` を省略した意味検索でも自分の回答は外します。探したいのは人が書いた発言なので、自分の要約文を混ぜると自分の言い回しに近いものを引きに行くことになります。

### 話題が並行しているときに混ざらないようにする

**会話の状態は持ちません。** 1リクエストは `runAgent({system, userContent})` の使い捨てで、メッセージ履歴を持ち越しません。「継続」は毎回チャンネルから組み直します。

以前はその材料が「返信1ホップ」と「直近30件をフラットに」の2つだけでした。話題が3つ同時に流れているチャンネルではこれで足りません — 30件がその混ざったログなので、**どの話の続きなのかをモデルが推測することになり、答えが混ざります**。

いまは**返信の鎖を最大6ホップさかのぼって**、今の話題だけを別の見出しで渡します。

```
## いま返信でつながっている話 (古い順・これが今の話題)
1) [08/11 20:39 たこ] デプロイの方針どうする
2) [08/11 20:39 sakana ←あなた自身の発言] CI が落ちてるのを先に直す話になってる ↩1

## このチャンネルの直近の会話 (古い順・背景。別の話題が混ざっている)
3) [08/11 20:41 あきら] 昼なに食う
4) [08/11 20:42 のあ] ラーメン
5) [08/11 20:43 たこ] モデル名隠すか迷ってる
```

見出しで役割を書き分け、プロンプト側でも「答えるのは1つだけ。混ぜて1つの答えにしない」と指示しています。行末の `↩N` がその番号への返信なので、背景の中の繋がりもそこで読めます。

**追加の API 呼び出しはほぼ発生しません。** 直近30件を先に取るので鎖のたどり先はキャッシュに載っており、載っていないぶんだけ `fetch` します。鎖に入った発言は背景から除くので、同じ発言を2回渡すこともありません。削除されていたら鎖はそこで切れます。

`query` を省略した意味検索も、鎖が2件以上あるならそちらを「いまの会話」として使います (直近12件のフラットなログでは、並行した話題が混ざった埋め込みになるため)。

### モデルとトークン

`deepseek-v4-flash` を OpenAI 互換の ChatCompletions で呼びます (`thinking` 有効 / `reasoning_effort=high`)。`low / high / max` の真ん中が `high` です。

トークンを使わないための作りが何点かあります。

| やっていること | 効果 |
| --- | --- |
| 呼ばれた時点で直近 30 件を最初から渡す | 「まとめて」系はツールを1回も呼ばずに終わる |
| プロンプトで「それで答えられるなら道具を呼ばずに答える」と明言する | 以前は書いていなかった (「強く言うと検索すべき質問にも答えてしまう」と考えていた)。実測で平均3.7往復・最悪35往復だったので、**さっさと答える方に振り直しました**。浅くなったらこの行を弱める |
| 19桁のメッセージ ID をモデルに見せず `[3]` の番号で扱う | 引用のたびに ID を書かせない |
| ユーザー ID ではなく表示名を渡す | 同上。誤爆メンションも防げる |
| 使えないツールは定義ごと出さない | アーカイブ未取り込み / Chrome 不在のとき丸ごと削れる |
| チャンネル一覧を prompt に載せず `channels` ツールにする | 探索しないターンでは払わない |
| ブラウザ操作を `browser` 1ツールの `action` に集約 | ツール定義15個ぶんの毎ターン課金を避ける |
| 空白・改行を畳み、ツール出力の本文を 300 文字で切る | 25件×複数回returnされるので、ここが効く |
| 最初から渡す直近の会話は 800 文字まで残す | 実測で平均 26.5 字・300字超はわずか 0.9% なので、切っても得がない。その 0.9% が長文=中身のある投稿 |
| 1リクエストの換算トークン予算 | 使い切ったらツールを外して、その場の材料で締めさせる (往復回数や文字数では縛らない) |
| system prompt を1文字も可変にしない | キャッシュは前方一致。時刻を入れていた頃は後ろ 5.5KB が毎回新規扱いだった |
| 可変な文脈 (時刻・チャンネル・呼んだ人) は user メッセージ側 | 同上。キャッシュできる前置きを system 1,811字 + ツール定義 4,127字 = 約2,800トークンに固定 |

スクリーンショットはモデルに渡さず、返信に画像として添付します。

### ツール

| ツール | 使えるとき | 何をするか |
| --- | --- | --- |
| `search` | 常時 | 過去ログ検索。`mode:keyword` (既定) は文字列一致、`mode:meaning` は意味が近い発言、`mode:count` は件数だけ (下記) |
| `read` | 常時 | チャンネルを時系列で読む。`at` に検索ヒットの番号・日付・メッセージ ID のどれでも渡せる。`direction:replies` で返信の連鎖もたどれる |
| `channels` | 常時 | 読めるチャンネルを発言数順に一覧する (エージェントは呼ばれたチャンネル以外の名前を知らない) |
| `browser` | 9222 に Chrome が居るとき | 専用 Chrome の操作 (下記) |

ツールは4つだけです。定義は**毎ターン送り直す**ので、数がそのまま固定費になります。実測で定義 JSON の**7割は JSON Schema の枠**（説明文は3割）だったので、文章を削るのではなくツールをまとめました: 検索系3つ (`search_messages` / `aggregate_messages` / `semantic_search`) を `search` の `mode` に畳んで **5266字 → 4127字**。`npm run check` に 4300字の上限アサーションを置いて、親切な1文ずつで元に戻るのを防いでいます。

#### キーワードで0件なら意味検索まで自動で走ります

`mode` という引数は無視され続けうるので、到達性を仕組みで担保しています。**キーワード検索が0件で、かつ `query` が単語ではなく文なら、同じ呼び出しの中で意味検索も続けて走ります。**

```
該当するメッセージはありませんでした (検索元: ローカル)。取り込みの穴かもしれない。
--- キーワードは0件。query が文だったので意味検索も続けて走らせた ---
意味が近い発言 4 件 (類似度 0.89〜0.81、候補 12,842 件)
以下は文字列一致ではない。断定する前に read で前後を読むこと。
```

キーワード側を先に「0件」と明言するので、モデルが「N件見つかった」と報告できません。撃つのは**0件のときだけ**で（件数が少ないのは正しく絞れているのが普通）、**1実行1回だけ**、モデルが自分で `mode:meaning` を使ったときは重ねません。

文か単語かの判定に形態素解析器は使いません。`by:term` が「漢字2文字以上はほぼ名詞」を使うのと逆で、**日本語は内容語が漢字/カタカナ、文法がひらがな**なので、ひらがなの密度と「内容語＋助詞＋内容語」の橋渡しで述語の有無を見ます。判定は意図的に甘めです（誤検知の代償はローカルのベクトル走査1回、見逃しの代償は機能そのもの）。22ケースの表を `npm run check` に固定しています。

#### `read` の起点は番号でも日付でもよい

`at` に **検索ヒットの参照番号 / メッセージ ID / 日付 (`2020-04`, `7d`)** のどれを渡しても動きます。`direction` は `around` (既定) / `before` / `after` / `replies`。

- **別チャンネルの発言を起点にできます。** `around` は「そのチャンネルに実在するメッセージ ID」でしか当てにできないので、他チャンネルの番号や日付が起点のときは `before` と `after` を2回引いて**挟み込み**ます（ID 比較として動くのはこちらだけ）。
- **`direction:replies` は返信の連鎖をたどります。** 「この発言に返信したのは誰か」は Discord の API では引けない（全件走査になる）ので、ここだけローカルの `reply_to` を使います。時系列に並べると返信は必ず親より後に来るので、`↩N` 表示がそのまま木の形になります。口論の判定で「誰が誰に答えていないか」を見るのに使います。
- **`expand:conversation`** で「無言で区切られたひとまとまり」まで広げます。閾値は固定せず**ページ内の間隔の中央値×6**（5分〜6時間でクランプ）から決めます。静かなチャンネルでは全部が別会話に、賑やかなチャンネルでは一晩が1会話になってしまうためです。会話がページの端まで続いていたらそう表示します（切れた会話を完結したものとして読まれないように）。

#### 検索元は2つあり、条件で自動的に決まります

| | Discord (既定) | ローカル (`source:archive`) |
| --- | --- | --- |
| クエリ | 単純なキーワード (と引用符付きの句) | `OR` / 除外 / 括弧 / 正規表現 / `reactions:>5` / `len:` / `hour:` / `weekday:` / `domain:` |
| 並び順 | `new` / `old` / **`relevance`** (Discord の関連度) | `new` / `old` / `reactions` / `long` / `random` |
| 集計・意味検索 | できない | できる |
| API 消費 | Discord の検索 API を消費 | ゼロ |
| 範囲 | Discord が持っているぶん (全期間) | 取り込み済みのぶん |

**既定は Discord 側**です。ローカルは取り込みが途中で止まっていることがあり、そのときの0件を「言っていない」と読まれるのがいちばん高くつく誤りなので、常に中身を持っている側を既定にしています。ローカルは**高度な検索**の担当です。

振り分けは `source` の指定ではなく**使った条件**で決まります。上の表でローカルにしか無い条件 (`regex:` / `OR` / `-除外` / `reactions:` / `len:` / `hour:` / `has:reaction` / `sort:reactions` など) が1つでも入っていれば、`source` を省略していても、`source:discord` と明示されていてもローカルに回します。**指定された条件を黙って落として検索するのがいちばん悪い**からです (「その条件で0件」と読まれてしまう)。回したときは1行目に理由を出します:

```
表示 8 件 ・ 検索元: ローカル (regex: はローカルのみ)
```

**勝手なフォールバックはしません。** どちらを引いたか分からないまま結果を読むほうが危ないので、結果の1行目に「検索元: Discord / ローカル」を必ず出します。

**検索結果は呼び出した人が見えるチャンネルに限られます。** `/search` と同じ権限スコープを通しています。Discord 側の検索は権限を見ないので、bot 側で実行者の権限で絞り直し、Discord が返す総ヒット数 (見えないチャンネルのぶんまで数えている) は**出しません**。落としたときは「読めないチャンネルのヒットは除外済」とだけ表示します。

`after:` / `before:` は Discord 側では `min_id` / `max_id` に変換して送ります。境界の意味は両方の検索元でそろえてあり、`after:2020` は 2020-01-01 **以降** (その日を含む)、`before:2021` は 2021-01-01 より前です。

### 話題を抽出する (`by:term`)

`search` に `mode:count by:term` を渡すと、その条件でよく話している**話題**が出ます。「探す語が事前に分からない」用途 (例: ある人の主張の食い違いを探す) の入口です。出てきた語を `search` の `query` に入れれば、その話題についていつ何と言っていたかを追えます。

```
author:daco by:term
  絶対: 40件 (全体比 8.0倍)
  品質管理: 40件 (全体比 8.0倍)
  レビュー: 40件 (全体比 8.0倍)
  型安全: 25件 (全体比 7.9倍)

author:daco after:2026-04-01 by:term
  型安全: 24件
  静的解析: 24件        ← 期間で絞ると話題が移っているのが見える
```

要点が2つあります。

- **形態素解析器を入れていません。** 辞書が重く依存も増えるので、文字種の連続を語の代わりに使います。日本語では動詞・形容詞が「漢字1+かな」になるため、**漢字2文字以上を要求するとほぼ名詞だけが残る**のがこれが辞書無しで成立する理由です。カタカナは3文字以上、ラテンは3文字以上 (`AI`/`PC` のような大文字2字だけ例外)。コードブロック・引用行・URL・メンションは除去します。
- **並べるのは頻度ではなく偏り**です。生の頻度では「する」「です」しか出てきません。サーバー全体の出現率を事前分布にした log-odds (z値) で並べるので、一般語は自動的に沈みます。全体比が 1.5 倍未満の語は出しません。

サンプリングは**期間を等分した層化抽出**です。`ORDER BY RANDOM()` は数百万行だと全走査になるので使いません。直近だけを見ると昔の話題が落ちて**立場の変遷が検出できなくなる**ので、全期間から均等に拾います。

**標本であることは必ず出力に書きます。** ここに無い語を「言っていない」と読まれると、この用途では結論が逆になるためです。閾値は `.env` で全部変えられます (実データで一度チューニングする前提の値)。

### チャンネルを横断する

サーバー全体を調べる用事のために、チャンネルを1つずつ覗いて回らない作りにしてあります。往復するたび会話全体を再送するので、往復回数がそのまま費用です。

- **`channels` で読めるチャンネルを一覧できます。** 発言数の多い順、`#general(15k) #dev(3.4k)` のような表記で、既定30件・`filter` で名前絞り込み。**呼び出した人に見えないチャンネルは出しません。** system prompt には載せず**ツールにしてある**のは、チャンネル数の多いサーバーだと一覧を毎ターン払うことになるためです（探索するときだけ1往復払う）。エージェントに最初から見えているのは呼ばれたチャンネル1つだけです。
- **`search` は最初から全チャンネル横断**です。「どこで話してたか」はまずこれで足ります。
- **`search mode:count by:channel`** でどのチャンネルの話題かを件数だけで把握できます (本文が返らないので安い)。
- **`read` は複数チャンネルを1回で読めます** — `channel: "general, dev, random"` で最大5つ。件数はチャンネル数で割って配分するので、出力量は1チャンネルぶんと同程度に収まります。
- **アーカイブ済みスレッドも読めます。** キャッシュに載っていないチャンネルは ID から取りに行くので、検索でスレッド内の発言がヒットしたらその前後も追えます。

想定している手順は「検索 → (集計) → 必要なチャンネルをまとめて読む → 特定の発言だけ `at` で掘る」です。チャンネル名自体を知りたいときだけ `channels` が挟まります。

### 往復回数は上限ではなくプロンプトで抑える

**往復の上限は持っていません** (`AGENT_MAX_ROUNDS` と `AGENT_MAX_TOOL_CHARS` は撤去しました)。代わりに `## 動き方` の4行で抑えます。

```
- 直近の会話は最初から渡してある。それで答えられるなら道具を呼ばずに答える。
- 呼ぶのは特定の事実が足りないと分かったときだけ。網羅しようとしない。
- 2〜3手で出なければ「出ない」と書く。語を当てずっぽうに変えて撃ち続けない。
- 会話全体を毎往復送り直すので、条件が複数あるなら1往復でまとめて呼ぶ。
```

本番48件の実測では**平均3.7往復・$0.0036** で、45件は6往復以下でした。壊れていたのは尾の1件だけです。

```
35往復 / 50 tool call / 入力 1,385,829 (キャッシュ 1,296,128) / 出力 34,104 = $0.0584
費用の内訳: キャッシュヒット入力 62% / 出力 16% / ミス入力 21%
```

**主因はツールの種類でも思考量でもなく、溜まったツール出力を毎往復送り直すことです。** 往復あたり平均 39,600 トークン、後半は 80k 超。だから 35往復は 3.7往復の16倍で、二次で効きます。中身は「当てずっぽうの語で20回以上検索」と「ヒットごとの `read around` 24回」で、`search {"author":"だこ","query":"会社 OR 法人 OR 登記 OR 売上 OR 収入 OR 年収"}` のような分野の思いつきを1往復ずつ撃っていました。

最後の1行 (`条件が複数あるなら1往復でまとめて呼ぶ`) が効率の要です。`runAgent` のツール実行は逐次 `await` なので、**1往復で並列に N 個呼んでも再送は1回**で、Discord REST も殺到しません。同じ50回の呼び出しでも 35往復に散らせば $0.058、10往復に束ねれば $0.008 で、**調査量は1件も減りません**。

上限で縛らないのは、往復と文字数では軽い往復と重い往復が同じ「1回」になって費用と合わないからです。機械的に残っているのは1リクエストの換算トークン予算と `HARD_ROUND_CAP = 100` (無限ループ専用) だけです。

### 意味検索 (ローカル埋め込み)

`mode:keyword` は文字列一致なので、**言い換えを跨げません**。

```
レビュー無しでマージするのは絶対にやめるべき
急ぎだから自分のPRはレビュー飛ばして通した
```

この2つは共通する部分文字列がほぼ無いので、trigram FTS では原理的に結び付きません。`mode:meaning` はこれを繋ぎます。実測:

```
=== キーワード検索 ("レビュー無しでマージ") ===
1 件ヒット   ← 言い換えには届かない

=== mode:meaning ===
意味が近い発言 3 件 / daco の中から (類似度 0.93〜0.83、候補 8 件)
埋め込み済み: このサーバーの 91%。ここに無い=言っていない、ではない。
(1位から離れすぎた 5 件は関連が薄いので除外した)
類似度は相対値。無関係な文でも 0.78 前後になるので、順位で見ること。
--- 時系列順 ---
1) [02/01 daco] レビュー無しでマージするのは絶対にやめるべき 近さ#1(0.93)
2) [07/01 daco] 急ぎだから自分のPRはレビュー飛ばして通した 近さ#2(0.85)
3) [07/11 daco] テストは後で書く、とりあえず動くので出す 近さ#3(0.83)
```

**外部 API は使いません。** `intfloat/multilingual-e5-small` (384次元) をローカルの CPU で動かします。`AutoModel` + mean pooling なので `sentence-transformers` は不要です。

`-base` (768次元) も試しましたが**採用しませんでした**。マージンが小さく (+0.027 対 small の +0.032)、推論は6倍遅く、RSS は 1.3GiB 対 1.0GiB でした。実測で small が勝ったので small です。

#### 類似度は絶対値で判断できない

実測で分かった一番大事な性質です。**無関係な日本語の文どうしでもコサインは 0.77〜0.82 出ます。**

| 比較 | 類似度 |
| --- | --- |
| 「レビュー無しでマージするのはやめるべき」↔「レビュー飛ばして通した」 | 0.85 |
| 同 ↔「猫の写真を貼っておきます」 | 0.78 |

つまり閾値では絞れず、意味があるのは**順位だけ**です。そのため、

- 各行に `近さ#2(0.85)` と**順位を併記**します。
- **1位から 0.1 以上落ちた候補は捨てます** (`SEMANTIC_RELATIVE_CUTOFF`)。これが無いと `limit` の枠を埋めるために無関係な発言が並び、モデルが「これも関連している」と誤読します。
- 出力に「類似度は相対値」と毎回書きます。
- 参照番号を渡された (「これに似た発言」) ときは、**その発言自身を候補から外します**。外さないと自分自身が常に1位 (類似度ほぼ 1.0) を占め、上の相対カットオフの基準を押し上げて本当に近い発言まで切り落とします。除外は rowid で突き合わせます — スノーフレークと比べても一致しません。

#### ベクトル化の単位は「会話のまとまり」です

1発言ずつではありません。Discord では主張が1発言に収まらないからです。

```
たこ: いや待って
たこ: レビュー無しで通すのはまずいって
さば: 急ぎなんだよ
たこ: 急ぎでも履歴に残らんのが問題
```

個別に埋めると意味を持つのは2行目だけで、残りは雑音になります。無言が続いたところで区切って、このやり取りを1ベクトルにします (`SEMANTIC_CHUNK_GAP_MS` 既定15分 / 20発言 / 1200字で分割)。

**実測して分かったこと** (合成会話8本で1発言単位と比較):

| | 1発言単位 | 会話単位 |
| --- | --- | --- |
| 言い換え側のマージン | 0.0159 | **0.0208** (+31%) |
| 言い換え側の順位 | 3位 / 38候補 | **2位 / 8候補** |
| ノイズ床 (無関係の平均) | 0.7988 | 0.8045 |
| 10字未満で埋め込まれない発言 | **53%** | 0% (吸収される) |

**ノイズ床は下がりませんでした** (むしろ僅かに上がった)。「0.78 のノイズ床は入力が短いせい」という仮説は否定されたので、閾値では絞れない前提は変えていません。効いたのは別の3つです。

1. **言い換え側のマージンが広がる。** ダブスタ検出で必要なのは「本人が最初に言ったこと」ではなく「後から言った逆のこと」が上位に来ることなので、効いてほしい側が効いています。
2. **候補が約5分の1になる。** 相対カットオフは「1位からの落差」で切るので、近い断片が枠を食い合わなくなります。
3. **短い発言が拾える。** 合成会話では**発言の53%が10字未満**で、1発言単位ではそれが丸ごと意味検索から消えていました (`SEMANTIC_MIN_CHARS=10`)。「いや待って」「まあ今回は例外」のような短文にこそ立場が出るので、ここが一番大きい差です。
4. **返るのが読めるやり取りになる。** 1発言単位の1位は「レビュー無しで通すのはまずいって」という断片で、意味を取るには `read` が要りました。

参照番号は**まとまり1つに1つ**（先頭の発言）付きます。やり取りごと出力に入るので多くの場合それで足り、足りなければ `read at:[番号]` で個別番号に降ります。

本文は保存しません。境界だけ持って、必要なときに `idx_msg_channel_time` の範囲スキャンで組み立てます。まとまりは複数人なので `author` は「その人の発言」ではなく**「その人が参加しているまとまり」**で絞ります（相手の反論込みで読めるので、この用途にはむしろ向いています）。

編集された発言を含むまとまりは夜間スイープで**ベクトルだけ捨てて埋め直します**。作り直す実装にすると、履歴の途中の1件が編集されただけでそのチャンネルの後ろ全部のベクトルを捨てることになります（実際にそれで4つのまとまりが3つに減るバグを踏みました）。編集は `created_at` を変えないので境界は動かず、同じ範囲を埋め直せば足ります。

#### query を省略すると「いまの会話」で引きます

`mode:meaning` で `query` を省略すると、直近の会話をそのまま query にして過去の似た会話を探します。**キーワードを人間が思い付く必要がない**のが要点で、`@bot これ前にも話した？` が成立します。

#### 運用

| | |
| --- | --- |
| ストレージ | int8 量子化 (ベクトル毎 scale) で **384 バイト/件**。1M 件でも +230MB |
| 速度 | 実測 **476 件/秒**。50万件のバックフィルで約 20 分 |
| メモリ | Python ワーカー約 1.0GiB。**10分使われないと落ちる**ので常駐しない |
| 起動 | cold start 6.9秒 / warm query **5ms**。ツールを出すとき先に温める |
| 対象 | bot 以外・10文字以上。URL はホスト名だけ残す (パスは雑音) |
| 追随 | 夜間 cron。on-write は 1GiB を24時間常駐させるのでやらない |

`/index embed` で作ります。開始前に「対象 248,300 件 / 推定 61 分 / 追加ディスク 115MB」を**実数で**出してから始めます。`/index status` に被覆率が出ます。

**権限は走査まで届きます。** 候補は `buildSearch` の SQL で絞ってからベクトルを引くので、呼んだ人に見えないチャンネルは走査対象にすら入りません (テストで固定済み)。

モデルを変えると既存ベクトルは全部意味を失うので、`embed_models` にモデルの同一性を記録し、旧モデルのベクトルは「無視される」だけで壊れません (`/index embed rebuild:true` で作り直し)。

> **注意**: `VACUUM` は rowid を振り直します。FTS も同じ依存を持つ既存の性質ですが、VACUUM 後は FTS の再構築と `/index embed rebuild:true` が必要です。

### 外付け Chrome (CDP)

bot のプロセスに Chrome を埋め込まず、**別プロセスの Chrome に CDP (既定 `127.0.0.1:9222`) で繋ぐ**だけの構成です。**この bot は Chrome を起動も終了もしません。** 居なければブラウザツールを出さないので、無ければ無いなりに動きます。

**推奨は bot と同じホストに専用 Chrome を1つ置くことです。** 人が普段使っているブラウザに相乗りさせると、そのログインセッションを Discord 経由で触らせることになり、タブを壊す事故も起きます。専用にすれば両方消えます。

起動方法は [deckide](https://github.com/tako0614/ide) の `agent-browser` に合わせています。要点は「headless を使わず、実 Google Chrome を Xvfb 上で headful 起動する」ことで、これは自動化検知 (Cloudflare の Managed Challenge 等) で弾かれにくくするためです。

```ini
# /etc/systemd/system/sakana-chrome.service の ExecStart で使う起動フラグ
xvfb-run -a --server-args="-screen 0 1280x720x24 -nolisten tcp" \
  /usr/bin/google-chrome \
  --remote-debugging-address=127.0.0.1 --remote-debugging-port=9222 \
  --user-data-dir=/var/lib/sakana-chrome/profile \
  --no-first-run --no-default-browser-check --disable-dev-shm-usage \
  --autoplay-policy=no-user-gesture-required \
  --disable-gpu-sandbox \
  --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader \
  --disable-blink-features=AutomationControlled \
  --lang=ja-JP --window-size=1280,720 --no-sandbox about:blank
```

- `--disable-gpu-sandbox` … GPU の無いサーバで headful 起動するために必要。
- **`--in-process-gpu` は付けないこと。** deckide は付けていますが (Chrome 149 では GPU プロセスの起動失敗で即死するのを回避するため必要だった)、Chrome 151 では逆効果です。GPU を browser プロセス内で動かすと ANGLE/Vulkan の初期化失敗がそのまま browser プロセスを殺し、`DevTools listening on ws://...` を出した直後に SIGTRAP (exit 133) で落ちます。GPU を別プロセスに残せば初期化失敗は無害に終わり、WebGL は SwiftShader で動きます。
- `--use-angle=swiftshader --enable-unsafe-swiftshader` … WebGL を実際に動かす。WebGL が無いのは実 Chrome として不自然で、検知の信号になる。
- `--disable-blink-features=AutomationControlled` … `navigator.webdriver` を立てない。
- `--no-sandbox` … unprivileged LXC で必要 (コンテナ側の権限を緩める代わりにこれで済む)。

CDP 側でも `navigator.webdriver` を `undefined` に保ち、`navigator.languages` を `Accept-Language` と揃える程度の補正を入れています。plugins や WebGL ベンダの**偽装はしません** — 不整合はかえって検知材料になるためです。

`browser` ツール1つに全機能を載せています: `open` / `text` / `links` / `html` / `screenshot` / `click` / `type` / `key` / `scroll` / `wait` / `eval` / `back` / `forward` / `reload` / `tabs` / `tab` / `new_tab` / `close_tab` / `console` / `network`、そして生の CDP を直接叩く `cdp` (`Page.printToPDF` など、ここに実装していないものはこれで呼べます)。

権限は2段に分けています。

- **誰でも**: `open` / `text` / `links` / `screenshot` / `scroll` / `wait` / `back` / `forward` / `reload` / `console` / `network`。ただし **Cookie を共有しない独立コンテキスト** (`Target.createBrowserContext`) に作った専用タブの中だけで、そのタブは**実行ごとに作って捨てます**。既存タブは読めず、ログイン済みサイトも引き継がず、他の人が開いたページや履歴も残りません。
- **`AGENT_BROWSER_TRUSTED_USERS` に書いた人だけ**: 上記に加えて `click` / `type` / `key` / `eval` / `cdp` / タブ操作。既定プロファイルの既存タブも触れます。

**「サーバー管理」権限では操作系を許しません。** モデレータ権限は普通に何人も持っているのに、生 CDP と `eval` は共有 Chrome に載っているログインセッションまで届きます。名指しの許可リストだけにしてあり、空なら誰にも出しません (`AGENT_BROWSER_FULL_FOR_ALL=true` で全員に開けますが、上の理由で推奨しません)。

#### 到達先の制限 (SSRF)

URL の判定は**名前ではなく解決した IP** で行います (`src/agent/urlguard.js`)。ホスト名の前方一致では守れません — `169.254.169.254` も `[::ffff:7f00:1]` (実体は 127.0.0.1) も `localtest.me` (DNS で 127.0.0.1 に解決される) も「`127.` で始まらない」ので素通りしてしまいます。

- スキームは `http` / `https` / `about:blank` のみ。`file:` / `data:` / `chrome:` / `devtools:` / `view-source:` は `AGENT_BROWSER_ALLOW_LOCAL=true` でも**開けません**
- `dns.lookup` で返った**全アドレス**を検査し、1つでもループバック / RFC1918 / `169.254/16` / `100.64/10` / `fc00::/7` / `fe80::/10` / NAT64 / multicast に当たれば拒否
- **リダイレクトとページ内 `fetch` も同じ関門を通します** (`Fetch.requestPaused` で1リクエストずつ判定)。入口の URL だけ見ても、302 で内部に飛ばされたりページ内 `fetch` の結果を DOM に描かれたりすれば本文として返ってしまいます。保険として、読み取る直前に着地先の URL を再検査します
- `cdp` から呼べる CDP メソッドは**許可リスト**制です。`Network.getAllCookies` / `Storage.*Cookies*` (Cookie の吸い出し)、`Browser.setDownloadBehavior` (ファイル書き込み)、`Target.*` (この関門を通らないタブの作成)、`IO.read` は通しません。`params.url` を持つメソッドは URL 判定を通します
- 誰がどの URL を開かせたかは `agent_tool_calls` に残します

**塞げていないこと**: 外部 URL を開ける以上、`https://ifconfig.me/all` のようなページを開かせれば**サーバーの外向き IP は見えます**。これは「貼られたリンクの中身を誰でも確かめられる」という仕様と引き換えです。止めるなら閲覧自体を許可リスト制にするしかありません。

### 使用量の制限

呼び出し回数ではなく**トークン**で制限します。詳細は[使用量の数え方](#使用量の数え方)。カウントは SQLite (`database.sqlite` の `agent_calls`) に残るので、再起動しても効きます。同時実行は3件までです。

#### 使用量の数え方

**勘定はトークン、意思決定はドル**です。

トークンで数えるのは、軽い一言と全期間の調査が同じ「1回」として数えられて費用と合わないから。**ドルで設定する**のは、「換算トークン500万」では高いか安いか判断できないからです。保存するのは生のトークン数なので、値上げされても過去の記録の意味が変わりません。

換算トークン1個は「キャッシュミス入力1トークン」で、重みは実単価の比です。`deepseek-v4-flash` は1Mトークンあたり 入力 $0.14 / キャッシュ $0.028 / 出力 $0.28 なので **0.2 と 2.0**。上限はこの換算レート (`AGENT_PRICE_IN_PER_MTOK`) でドルからトークンに直します。

本番の実測 (`agent_calls`)。プロンプトを直す前後で1回あたりの費用が変わりました。

| | 件数 | 平均往復 | 平均 | 最悪 |
| --- | --- | --- | --- | --- |
| 変更前 | 48 | 3.7 | $0.0036 | 35往復 **$0.0584** |
| 変更後 | 57 | 2.4 | **$0.0024** | 11往復 **$0.0116** |

「さっさと答える」「条件が複数なら1往復でまとめて呼ぶ」を入れただけで**1回あたり33%安く、最悪値は5分の1**になりました。上限は入れていません。

既定の上限はこの実測に合わせています。

```
全体/24h        $0.50   平均 $0.0024 なら約200回 → 請求は最大 $15/月
1人あたり/24h   $0.05   約21回。全体の 10% なので、10人が同じだけ使ってようやく全体に当たる
1リクエスト     $0.02   暴走ガード。実測の最悪 $0.0116 の1.7倍
```

**1人あたりは以前 $0.25 でした。** 平均 $0.0024 だと1人で約104回、しかも全体 $0.5 の半分なので、**2人で全体が尽きます**。1人あたりを全体の 10% に絞ったので、1人の使い方で他の人が止まることがなくなりました。

1リクエストの上限 ($0.02) は1人あたり/日 ($0.05) より小さくしてあります。1回で1日ぶんを使い切れると、暴走1回でその人が締め出されるためです。

数字は `npm run check` で直書きしていません (既定を絞ったときに落ちたので、上限と1回のコストから何回もつかを計算して照合します)。実行中に変えるなら `/agentlimit set user_daily_usd 0.03` で、再起動は要りません。

窓は暦の日ではなく**直近24時間の移動窓**です。深夜0時のリセット待ちが生まれないうえ、1時間窓だと1日に24回リセットされて請求の長さを測っていないためです。

**管理者 (`ARCHIVE_ADMIN_USERS` / Administrator / ManageGuild) は判定そのものを通らず、全体の集計にも乗りません。** 乗せていた頃は、運営が重い調査を続けるほど他の人が「サーバー全体の上限」で止まりました。行は残るので支出としては見えます。

信頼した人だけ上げたいときは `/agentlimit grant user:@someone usd:0.2` で、再起動なしに個別の上限を付けられます。

**上限を絞った直後は `/agentlimit reset` で窓を空けられます。** 絞る前に使っていた人が、その瞬間から締め出されてしまうためです。`user:` を付ければその人だけ、省略すれば全員。

リセットは行を消しません。`counted = 0` の印を立てるだけです。消してしまうと「なぜこの月これだけ請求が来たか」を追えなくなるので、**上限の判定に数えない印**と**支出の記録**を分けています。`/agentlimit show` は判定に乗らないぶんがあるときだけ「実支出」の欄を足します。

1リクエストの予算を使い切ったときは「打ち切りました」で終わるのではなく、**ツールを外してその場の材料で答えを書かせます**。往復の上限は `HARD_ROUND_CAP = 100` がコードに埋まっていますが、これは無限ループ専用の最後の壁で、つまみとしては出していません (予算で止まるのが普通の経路)。

**リクエスト全体の時間制限は持ちません。** 以前は 150 秒で畳んでいましたが、それは「トークンぶんは払ったのに謝り文だけ返す」経路でした。時間で止めるのをやめて、止めるのはトークンだけにしています。応答が来ないソケットは1回の呼び出しごとに `AGENT_HTTP_TIMEOUT_MS` で畳み、失敗にはせず引き直します。

結果として待ち時間の上限は「予算 ÷ 1往復のコスト × 1往復の時間」で決まります。実測の最悪は11往復で、予算 $0.02 に当たるのはその手前です。

金額はあくまで見積りで、請求と一致する保証はありません (キャッシュヒットの判定は API のレスポンス頼り)。突き合わせはしていません。

- `/agentlimit show` — いまの使用量と上限をドルで表示 (誰でも)。単価と重みも出すので、入れ間違いに気付けます
- `/agentlimit set key:<項目> value:<値>` — 実行中に上限・単価・重みを変える (`/index` と同じ管理者判定)。`value` を省略すると `.env` の既定に戻ります
- `/agentlimit grant user:@someone usd:1.0` / `revoke user:@someone` — 特定の人の1日上限を上げる / 取り消す

トークンは実行が終わるまで分からないので上限は後追いです。超過は「同時実行数 × 1回ぶん」で有界です。途中で失敗した実行も、払ったトークンは記録に残します (150秒でタイムアウトした9往復ぶんをゼロとして捨てると、請求と乖離していきます)。

## メッセージアーカイブと検索

サーバーの過去ログを SQLite に取り込み、Discord 標準検索ではできない条件で検索できるようにします。

### 取り込み (管理者)

```
/index build     全チャンネル・全スレッドを最古まで遡って取り込む
/index update    前回の続きから最新分だけ取り込む
/index status    進捗・チャンネル別の件数・エラーを確認
/index verify    取りこぼした期間 (bot 停止中など) を探して埋める
/index repair    全文検索の索引を検査し、壊れていたら作り直す
/index embed     意味検索用のベクトルを作る (rebuild:true で作り直し)
/index cancel    実行中の取り込みを中止
/index reset     このサーバーのインデックスを全削除 (確認ボタンあり)
```

- `build` は中断しても大丈夫です。チャンネルごとに「どこまで遡ったか」を保存しているので、もう一度実行すると続きから再開します。
- 一度取り込んだあとは、新しいメッセージ・編集・削除・リアクションを自動で追記するので、基本的に `/index update` は不要です。
- Bot が読めないチャンネルは自動でスキップし、完了時に一覧を出します。

`/index` は「サーバー管理」権限を持つ人か、`ARCHIVE_ADMIN_USERS` に ID を書いた人だけが実行できます。Discord の `default_member_permissions` で絞ると許可リストの人からもコマンド自体が見えなくなる（入力候補に出ない）ので、**可視性は開けて実行可否をコード側で判定**しています。権限の無い人が叩いても断られるだけで何も起きません。

`ARCHIVE_ADMIN_USERS` を使う理由は、サーバーの ManageGuild を渡すとサーバー名変更・招待・Webhook・連携の管理まで付いてしまうためです。bot の管理コマンドだけ渡したいときはこちらを使ってください。

### 全期間を取りこぼさない

「取り切った期間」をチャンネルごとに**区間**として記録しています (`channel_spans`)。単一カーソルだけだと、bot が落ちている間に流れた分を復帰後の最初の1通がカーソルごと飛び越えてしまい、**その穴は二度と埋まらず `/index status` からも見えません**。区間で持てば穴を列挙して塞げます。

- **起動時と再接続時に自動で追いつきます。** 落ちていた間の分はここで取りに行きます。
- **新着メッセージで区間を伸ばすのは、そのチャンネルの追いつきが済んでいる間だけ**です。切断を検知したら印を捨てるので、繋がっていなかった期間を「取った」ことにしません。
- `/index status` に**被覆**が出ます。穴があれば件数と合計時間、多い順にチャンネルを表示します。
- `/index verify` で穴を埋めます (複数回ダウンした場合など、末尾以外の穴も対象)。
- **区間が1本も無いチャンネルは「追いつき済み」にしません。** 区間管理を入れる前に取り込んだチャンネルと live indexing だけで作られたチャンネルがこれに当たり、印だけ付けて帰ると復帰後の最初の1通がダウン期間を「取った」ことにして穴を永久に隠します。手持ちの範囲を初期区間として1本作ってから追いつきます。
- **「先頭まで遡れていない」は区間の隙間には出ません** (半分だけ取り込んだチャンネルは連続した1本の区間に見えるため)。チャンネル作成時刻 (snowflake) と最古の取り込み済みメッセージの差を `/index status` に別途出し、`/index verify` で続きを取ります。
- 全文検索の索引はコード経路では本体とずれませんが、`VACUUM` や dump からの復元は rowid を振り直すので、**件数は合っているのに古い行だけ引けない**状態になり得ます。完全に無症状なので `/index repair` で検査・再構築できるようにしています。

区間演算はメッセージ ID の文字列比較ではなく snowflake から取り出した時刻で行っています。snowflake は 17〜19 桁あり、**桁数が違うと文字列比較の大小が実際の時系列と逆になる**ためです。

**限界**: 削除されたメッセージは Discord 側にも残っていないので復元できません。「全期間保有」はこの意味で完全ではありません。bot に閲覧権限が無かった期間の分も取れません (権限が付いたあとの `/index build` で入ります)。アーカイブ済みスレッドの列挙は 200 ページで打ち切ります。

### 検索 (全員)

`/search` は誰でも使えますが、**実行者が閲覧できるチャンネルの結果しか返しません**。見えないチャンネルの中身が検索経由で漏れることはありません。

Discord 標準の検索と違って、こういう条件が使えます。

| 書き方 | 意味 |
| --- | --- |
| `会議 OR ミーティング` | どちらか (標準検索は AND だけ) |
| `会議 -中止` | 除外 |
| `(猫 OR 犬) かわいい` | 括弧でグループ化 |
| `"明日の会議"` | 空白込みの部分一致 |
| `reactions:>5` | リアクションが5個より多い |
| `reaction:👍` | 特定のリアクションが付いている |
| `len:>200` / `len:<10` | 文字数 |
| `hour:22-4` | 深夜帯の発言だけ |
| `weekday:sat,sun` | 土日の発言だけ |
| `domain:github.com` | 特定サイトの URL が貼られたもの |
| `regex:/^\d+$/` | 正規表現 (本文のみ。空白や `)` 単体を含むなら `regex:"/a b/"` と引用符で囲む) |
| `sort:reactions` | 反応が多い順に並べる |

標準検索と同じ条件も一通り使えます: `from:` `in:` `mentions:` `replyto:` `before:` `after:` `during:` `has:` `is:`。

日本語は3文字以上なら FTS5 の trigram インデックスを使い、1〜2文字の語は `LIKE` にフォールバックします (件数が多いと少し遅くなります)。

`in:#channel` はそのチャンネルのスレッドも含めて検索します。

### 削除されたメッセージ

取り込み後に削除されたメッセージは、消えたことを記録したうえで検索結果から除外します。`is:deleted` で明示的に探せますが、これは「メッセージの管理」権限を持つ人だけです。

### 設定

```env
ARCHIVE_DB_PATH=archive.sqlite      # アーカイブの保存先 (XP 用 DB とは別ファイル)
ARCHIVE_TZ_OFFSET_HOURS=9           # hour:/weekday:/日付指定を解釈するタイムゾーン
ARCHIVE_FETCH_DELAY_MS=150          # 取り込み時の待ち時間 (小さくすると速いがレート制限に当たりやすい)
ARCHIVE_REGEX_BUDGET=300000         # regex: 1回あたりの最大走査件数
```
