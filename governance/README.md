# 統治ルールの境界

統治の政治的な値と手続は、現行憲法の末尾にある一つの
`governance-rules` JSONブロックを正本とします。`policy.json`は旧憲法との
互換と初期値の検査用であり、新しいサーバーでは憲法内の規則から同じ形へ
投影されます。

コードが固定するのは、監査記録、入力schema、Discordの実在する権限と上限、
未知handlerの拒否、待機なし循環の拒否など、実行を安全にする技術的な境界です。
討議期間、無風期間、異議の必要数、成立判定の席と必要票、施行後の停止の必要数、
改憲の保留期間、投票条件、AI席数、処分上限、承認数、上訴範囲および状態遷移を
変更するには、完全な憲法改正案として公開討議、違憲審査、成立判定を通します。

AI席だけで成立させる手続を宣言する実行規則は、人間が止める手段を必ず持たなければ
なりません。法律は施行後の停止（`workflows.law.config.suspensionRequired`）、
憲法改正は施行前の保留（`enactment_hold`）です。この二つを外した規則は、
改憲手続を通っても成立しません。

## 立法受付

AI席が成立を決める憲法では、`@立法`への依頼はその場で案件にならず、次の国会の
意見として記録します。国会は開会時に、席の必要票で意見ごとの採否を決め、
棄却した意見にも理由を公開します。採用した意見だけを起草へ回します。

起草へ回す前に、進行中案件、現行法、現行憲法と比較します。三つの独立したAI席の
うち実行規則で定める必要票が一致した場合だけ、次のいずれかへ振り分けます。

- 現行法で実現済みなら法令集へ案内する
- 同じ目的または競合する対案なら既存の公開討議へ加える
- 現行法の変更なら、その法律の完全な次版として起草する
- 憲法の変更なら、現行憲法の完全な次版として起草する
- 独立して成立できる関連案または無関係な案だけを新規案件にする
- 必要票に達しない場合は具体化を求め、正式案件を作らない

候補本文と利用者の入力はすべて未信頼データです。AIが候補にない対象ID、
未知の権限、未知のhandlerまたはschema外フィールドを返しても受理しません。
法律と憲法は受付時の対象hashを固定し、並行する別案が先に成立した場合は、
古い全文で上書きせず最新版を基礎にした再討議を求めます。
